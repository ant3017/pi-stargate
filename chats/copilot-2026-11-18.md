# pi-stargate — Raspberry Pi Gateway and GitHub Connectivity
## Date: 2026-11-18

## Context

The Raspberry Pi gateway provides the `sg0` access point on `ap0`, uses
`eth0` or `wlan0` for uplink, and routes ordinary traffic through the
WireGuard interface `wh0`. The laptop had been connected through the Pi when
`git push` to GitHub failed with a connection reset.

## Earlier gateway troubleshooting

- Fixed hostapd startup by adding a systemd drop-in to pass the hostapd config
  path. The AP also needed its channel synced to the uplink Wi-Fi channel.
- Made AP channel synchronization idempotent so repeated networkd dispatcher
  events would not continually restart hostapd.
- Changed dnsmasq AP and USB configurations to `bind-dynamic`, preventing
  startup failure when `usb0` did not yet exist.
- Added WireGuard firewall/routing rules so a WireGuard client connected to
  `ap0` can send its own handshake directly through a physical uplink rather
  than recursively through the Pi's WireGuard tunnel.
- The laptop subsequently obtained a DHCP lease and gateway/DNS at
  `192.168.50.1`; gateway pings and DNS worked. HTTP/HTTPS to `example.com`
  worked, even though ping to public IPs was unreliable.

## GitHub connection diagnosis

The laptop's `git push` failed while connected to `sg0`. GitHub's HTTPS/TLS
connection stalled from the Pi on its default route, while HTTPS to
`example.com` succeeded. The Pi had a WireGuard policy route sending ordinary
traffic through `wh0`; its physical Ethernet default route was via `eth0`.

Follow-up, read-only tests on the Pi confirmed:

- `https://github.com/` timed out during TLS when using the default route or
  explicitly binding to `wh0`.
- `https://github.com/` succeeded when binding to `eth0`.
- This difference persisted when both interfaces connected to the same fixed
  GitHub IP addresses, separating the route from DNS/address selection.
- HTTPS to `example.com` succeeded through `wh0`.
- `git ls-remote` to the repository timed out using the default route.

The user then connected the laptop directly to the router (not through the
Raspberry Pi) and successfully completed the Git operation. This confirms the
problem is specific to the Raspberry Pi's connection/path to GitHub, rather
than the laptop's Git setup.

## Outcome / next investigation

No configuration was changed during the final GitHub route diagnosis. The
Pi's GitHub traffic through WireGuard is the failing path; direct `eth0`
access works. Investigate the WireGuard server/egress path or any route- or
destination-specific filtering before changing gateway configuration. Do not
include or expose WireGuard private keys in notes or diagnostics.
